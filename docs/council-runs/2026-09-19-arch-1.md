## Proposal 1 · needs-review · proposed by crowelm-zenith

Step 1: Establish one mandatory host-side authorization boundary for every Room action, before adding distributed execution or parallel rounds.

Evidence and rationale: rooms/registry.js defines effectiveTier as the minimum of roster ceiling and configured autonomy, but rooms/council-host.js checks configured autonomy for file grants without calling that function. Its authorized callback rechecks sign-in, run ownership, workspace and roster/model pins. rooms/council.js binds approvals to the grant, snapshot and proposal; rooms/council-files.js rechecks authority at the write boundary. These are valuable council-specific controls, not evidence of uniform enforcement across other dispatch paths. docs/COUNCIL-AUTOPILOT.md explicitly excludes shell, MCP and browser actions from council authority. Implement a common authorization boundary without expanding those supported actions.

Decision: Every built-in tool, MCP connector invocation and remote companion command attributable to a Room must pass through a trusted dispatch gate, with enforcement at the component holding the execution credential or resource. Model output, renderer arguments, connector annotations and pairing status cannot establish authority. Unmanaged connectors that cannot be mediated must be unavailable to Rooms, not merely omitted from tool listings.

Interface: Introduce a host-created ActionIntent containing actionId, roomId, authenticated principal, grantId when applicable, authorityRevision, adapterId, operation, normalized target and argumentDigest. A trusted operation registry supplies effect class and required permission; unknown operations fail closed. authorizeAndDispatch(intent) resolves current Room policy, all roster identities, global autonomy, resource scope and any applicable grant. Permission is the intersection of these constraints. Reject unresolved roster identities and invalid tiers at this boundary rather than relying on registry.js behavior that filters unknown agents and defaults invalid configured tiers to edit. Bind dispatch to the exact operation, arguments, target and authority revision. Remote execution requires receiver-side validation against current authority; a caller's allow decision or paired-device identity alone is insufficient. If current authority cannot be established, deny.

Semantics and invariants: A Read-only Room may perform explicitly permitted, classified reads, but cannot mutate resources, run arbitrary commands or use an unknown-effect operation through any adapter. Plan mode cannot invoke resource tools. An explicit council file grant cannot override a Read-only Room ceiling. Advisory councils retain only inference and internal result recording, with no external action. Preserve tool-free council inference, pinned models, stale-evidence rejection, exact file scope, expiry, revocation and per-write authorization checks. Council quorum never grants additional permissions. Check permission immediately before the effect; adapters unable to honor that boundary remain disabled. Revocation blocks subsequent dispatches but cannot undo effects already committed.

Audit contract: Emit structured authorization and dispatch receipts with actionId, roomId, adapter, operation, policy revision, decision, reason code and decision/dispatch/outcome timestamps. Record denied attempts too. Do not log raw credentials or unrestricted arguments. These receipts provide a foundation for later coverage and intervention metrics, not proof of full coverage by themselves.

Verification and acceptance: Inventory actual built-in, MCP and companion dispatch entry points before claiming coverage; those implementations are not supplied here. Add boundary tests for each adapter using the same permission matrix, including global Execute plus a Read-only roster, unknown identities, forged Room context, direct connector invocation, stale revisions, permission changes between approval and dispatch, disconnected receivers and pairing without a grant. Require zero prohibited adapter effects, recorded denials and regression coverage for existing council file safeguards. Test an allowed read and an authorized scoped edit to detect blanket-denial regressions. These are proposed tests, not observed results.

Limits and build order: This boundary does not sandbox hostile external processes, make arbitrary connector metadata trustworthy, or introduce new council execution modes. Its guarantee covers only mediated entry points, so unmediated routes must be disabled before release. Subsequent bounded decisions should address, in order: durable cross-device state with fenced execution and no interrupted-action replay; atomic dollar reservations and real provider-cost settlement on every runner; independent adversarial review and untrusted-evidence isolation; and calibrated oversight metrics with release acceptance criteria. This is the first proposed decision, not a claim that the council has already agreed to the complete plan.
