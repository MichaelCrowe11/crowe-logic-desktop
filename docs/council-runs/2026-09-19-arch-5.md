## Proposal 1 · rejected · proposed by crowelm-zenith

Step 3a establishes spend admission at the authoritative owner from Step 2, behind Step 1 authorization. Start with rooms/engine.js for shared admission and fan-out preparation, and rooms/council.js for an operator-approved grant maxUsd and cycle funding. Integrate the request boundary in rooms/council-host.js and the web adapter before enabling funded execution. The host and docs/COUNCIL-AUTOPILOT.md are not supplied here; references to their behavior rely only on quotations in the supplied council-run documents. Adapter integration remains proposed, not verified.

Prepare each outgoing request completely before admission: pinned deployment and tokenizer revision, system messages, history, evidence, tool schemas if applicable, provider framing, and generation parameters. Obtain its exact billable input-token count from a provider-compatible tokenizer or authoritative counting endpoint. Character ratios are forbidden. Counting must include everything the gateway adds; otherwise refuse that route. Any charge for counting itself requires a separately bounded reservation. Freeze the prepared request and bind its digest to the count, price revision and reservation. Changes require fresh counting and admission.

Require a trusted, current pricing contract covering every billable category. For a supported text request, reserve R = roundUp(inputTokens * inputRate + maxOutputTokens * outputRate + boundedAdditionalCharges), using integer monetary units and conservative rounding. Cache discounts cannot reduce this ceiling unless guaranteed. The outgoing provider request must carry the enforced maxOutputTokens, including billable reasoning tokens where applicable. Disable routes whose providers cannot enforce that total, whose hidden charges lack bounds, or whose billing/counting semantics are unknown. Local stream truncation is not an output-cost cap. No transparent retries, model substitutions or extra inference calls may bypass admission.

In one durable owner transaction, admit only when R <= min(Room budget minus Room committed spend minus outstanding Room holds, grant maxUsd minus grant committed spend minus outstanding grant holds). A council reservation debits both limits, not two independent allowances; other Room activity competes for the same Room balance. Validate both caps as finite nonnegative amounts, with zero meaning no spending, never unlimited. Missing council maxUsd refuses a new run. Cap reductions below committed spend plus holds are rejected; neither clients nor models can increase a grant. Bind each hold to roomId, grantId when applicable, owner epoch, authority revision, callId and request digest. Persist before sending, recheck authority and pricing validity at dispatch, and refuse on persistence failure. Unresolved dispatched holds remain charged against availability across recovery, without replay.

For speak, forward, critique and revise, freeze and count every request in the intended parallel batch, then reserve their sum atomically before any fan-out. Insufficient funds dispatch none of that batch. Each later tool round or retry is another counted, reserved batch, not an implicit entitlement inside runAgent.

Council prompts depend on responses not yet generated, so do not pretend their future token counts are exact. Before the proposer runs, escrow a complete cycle using a certified maximum accepted input-token count Imax and enforced output cap Omax for each proposer, classifier, reviewer and verifier slot. The cycle ceiling is the sum of roundUp(Imax * inputRate + Omax * outputRate + boundedAdditionalCharges) for those slots. Imax is a hard adapter input limit, not a prediction: reject any materialized request above it, without truncating approved evidence. If no certified bound exists or the whole escrow does not fit both balances, send no proposer request. Once each prompt exists, count it exactly and allocate its exact reservation from its escrow slot; allocation must not add a second hold. Keep unused slot capacity until the cycle closes. Recompute and fund each subsequent cycle before it starts. Existing maxCalls, maxSteps, expiry and no-replay checks remain independent constraints. Oversized evidence can still stop a funded cycle; escrow guarantees funding capacity, not successful completion.

Proposed acceptance tests capture actual outgoing requests and prove count/digest identity, provider output-cap transmission, rejection of unsupported counting or pricing, atomic refusal of an unaffordable parallel batch, contention between two grants and ordinary Room calls, exact-boundary rounding, durable holds after crashes, and refusal before proposing when full-cycle escrow cannot fit. Exercise a future prompt at Imax and one above it, with the latter sending no request. These are tests to implement, not observed results. This advisory step records admission requirements only; Step 3b separately specifies settlement, stale-price refusal and recording on every runner. Do not enable the strict-ceiling feature until both steps are implemented and verified.
