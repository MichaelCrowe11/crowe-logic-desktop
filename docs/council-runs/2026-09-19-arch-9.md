Size bounds for anything shown are those in docs/council-runs/2026-09-19-protocol-bounds.md (reasons at most 4000 characters, summaries at most 8000); the metrics view truncates to them and adds no new limit.

Decision and placement: add a pure `metrics(state)` in rooms/council.js beside `create` and `recover`, exported, with no clock or I/O, taking the persisted council state (and the Step 1 authorization receipts once they exist). rooms/council-host.js returns it from the `state` command so the renderer shows it in council run detail; nothing is written.

Metrics and the events that feed them:
1. Action coverage. Numerator: executed events whose item has a receipt (advisory `recorded`, or file paths with sha256). Denominator: approved events. Council-internal coverage must be 1.0 by construction; a gap means an approval that ran without a receipt. Product-wide coverage is Step 1 receipts over Step 1 ActionIntents; until Step 1 lands the view labels coverage as council-only.
2. Intervention latency. From the `at` of the last phase or call event to the `at` of the paused or revoked event. Known gap: `stop()` sets status and revision but records no timestamp; the event is written only when `check()` throws inside `run()`. Add `stoppedAt` in `stop()` so latency measures operator request to run halt, not halt to persistence. Escalation latency is the same span ending at the escalated event.
3. False approvals. Items with status needs-review (approved and executed, then verification decision not approve), plus items marked by the operator as reverted after verified. Also, once Step 4 hostFacts exist, any approve ballot whose reason contests a host fact. Fed by approved, executed, verified, escalated.
4. False refusals. Items with status rejected where every reject ballot has Step 4 basis design or missing-evidence (normalized to abstain going forward; counted from history), items blocked or escalated by a classifier with category design, and rejects whose reason contradicts hostFacts (the 3429 counted as 3812 case). Fed by vote, safety, escalated.

Invariant: metrics are derived, deterministic and recomputable from the persisted state; they grant nothing, change no status and are never sent to a model. Every count cites the item hash so an operator can open the proposal it came from.

Proposed tests: synthetic states in the council test harness with a fake clock: one approved and executed item yields coverage 1.0; an approved item without receipt yields below 1.0; a paused run reports latency equal to the injected gap; a needs-review item counts one false approval; a rejected item with only design-basis ballots counts one false refusal; a second call to metrics on the same state returns identical output.

Known limit: false approvals and false refusals need a label the machine cannot supply; verifier disagreement and operator revert are proxies, not ground truth.
