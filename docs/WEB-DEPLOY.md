# Deploying the web build to crowelm.com/app

The web build is the desktop renderer served as static files behind the edge
on the `crowelm-chat` VM. Nothing builds on the server; the files in
`renderer/` are copied into the directory Caddy serves and Caddy is reloaded.
This page exists because the first deploy of these files was done by hand and
recorded only in a session transcript, which is not a place to keep a
procedure.

## What ships

Eight files, and every deploy ships all eight:

    renderer/app.html        the web entry point (hand-maintained)
    renderer/web-bridge.js   window.crowe over HTTP; the plan and the paywall
    renderer/web-ui.js       the web chrome: honest first-run copy, hides the
                             tiers the browser refuses, a Workspace link, the
                             plan card and the Upgrade pill
    renderer/rooms-web.js    the room engine, bundled (generated; see below)
    renderer/renderer.js     the shell, shared with desktop and mobile
    renderer/styles.css      the stylesheet, shared with desktop and mobile
    mobile/src/mobile.css    the phone layer: one column under 820px, shell
                             rules under body.mobile; served as mobile.css
    mobile/src/mobile-ui.js  the phone chrome: tab bar, scrim, keyboard insets;
                             loaded by app.html only on a coarse pointer or a
                             narrow screen; served as mobile-ui.js

`renderer.js`, `styles.css`, `mark.js` and `mark-geometry.js` are the same
bytes the desktop ships. `styles.css` used to be left out of this list on the
theory that it never changes between deploys; it did (the session-brief editor
landed with its rules), and the VM served the renderer with a stylesheet one
commit behind it from 2026-08-15 to 2026-08-22. It ships every time now.
`mark.js` and `mark-geometry.js` change rarely; ship them when `git log` says
they did. If a deploy touches `renderer.js` it must be the committed version,
never a local edit, because the desktop and mobile suites hold that file to
their own contracts.

`rooms-web.js` is generated by `scripts/build-rooms-web.js` from `rooms/`.
`npm test` fails while it is stale, so a passing test run is the check that
the file about to ship matches the engine in the repo.

## Where they go on the VM

Caddy serves `/app` from its config volume:

    /var/lib/docker/volumes/caddy_config/_data/crowe-app/renderer/

which the caddy container sees as `/config/crowe-app/renderer/`. Files are
root-owned and world-readable. The path is inside a Docker volume rather than
`/srv` because that is where the first deploy put it; moving it is a Caddyfile
change and a copy, and is not worth doing until the identity change to the
same Caddyfile lands (see `crowelm-platform/docs/identity/`).

## Procedure

`scripts/deploy-web.sh` runs steps 1 to 3 below and then compares the hash of
every shipped file on the VM against the working tree, so the deploy is
verified by the artifact and not by the exit code of `scp`. The steps stay
written out here so the script can be checked against them.

All of the below is one command now: `bash scripts/deploy-web.sh` (and
`--verify`, `--rollback`). It refuses uncommitted renderer files and a stale
rooms bundle, takes the dated backup, reloads Caddy, and checks the served
engine hash and stamp against HEAD when `CROWE_APP_AUTH=user:pass` is set in
your shell for that one command. The steps are kept here so the script can be
read against them.

Run from a checkout of this repo on the branch being deployed, with `npm test`
green. Each command is one line and each is safe to rerun.

1. Confirm what you are about to ship is what is committed:

       git status --short renderer/ && git log -1 --format='%h %s'

   `git status` must print nothing under `renderer/`.

2. Copy the four files to the VM's `/tmp`:

       scp -i ~/.ssh/google_compute_engine renderer/app.html renderer/web-bridge.js renderer/web-ui.js renderer/rooms-web.js renderer/renderer.js renderer/styles.css mobile/src/mobile.css mobile/src/mobile-ui.js crowelogic@crowelm-chat:/tmp/

3. Install them into the served directory, with a dated backup of what was
   there, and reload Caddy so the cache-busting query string is honoured:

       ssh -i ~/.ssh/google_compute_engine crowelogic@crowelm-chat 'D=/var/lib/docker/volumes/caddy_config/_data/crowe-app/renderer; sudo mkdir -p $D/.bak-$(date +%Y%m%d-%H%M%S) && sudo cp -a $D/*.js $D/*.html $D/.bak-$(date +%Y%m%d-%H%M%S)/ 2>/dev/null; for f in app.html web-bridge.js web-ui.js rooms-web.js renderer.js styles.css mobile.css mobile-ui.js; do sudo install -m 0644 -o root -g root /tmp/$f $D/$f && rm -f /tmp/$f; done && sudo docker exec caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile && echo deployed'

4. Verify from outside. Signed in (the edge asks for credentials), in the
   browser console at https://crowelm.com/app:

       (await (await fetch("/app/renderer/rooms-web.js")).text()).slice(0, 120)

   must show the generated-file header with the same engine hash that
   `node scripts/build-rooms-web.js --check` prints locally, and

       window.CroweRooms.source

   must show the same three hashes.

5. Smoke a room: open Rooms, create one from a template, address `@room`, and
   watch two seats stream. Cost shows 0 on the web; the ledger prices runs, the
   browser does not.

## Rollback

The backup directory from step 3 holds the previous files. Copy them back over
and reload:

    ssh -i ~/.ssh/google_compute_engine crowelogic@crowelm-chat 'D=/var/lib/docker/volumes/caddy_config/_data/crowe-app/renderer; B=$(ls -d $D/.bak-* | tail -1); sudo cp -a $B/* $D/ && sudo docker exec caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile && echo "rolled back to $B"'

## The plan, and the money

Sign-in is Crowe ID at the edge (oauth2-proxy; `crowelm-platform`
`infra/crowelm-chat/`). The plan is the Keycloak user attribute `crowe_tier`,
carried by oauth2-proxy as the groups claim (`oidc_groups_claim`) and copied
onto every `/app` request as `X-Auth-Request-Groups`. From there:

- `/app/whoami` answers `{"email","tier"}`. `web-bridge.js` reads that and
  the older bare-email text, so either side can be applied first.
- `/app/owui/api/chat/completions` and `/app/gw/*` answer **402** for a free
  tier. The bridge turns that into one line in the transcript and a
  `crowe:paywall` event; `web-ui.js` opens the plan card on it.
- The plan card reads the price from the checkout Worker's `/v1/catalog`
  (`~/crowe-checkout`, the estate's one ladder; Pro is the `pro` rung) and
  POSTs `/v1/checkout {slug, email}` with the signed-in email. The Worker
  mints a Stripe Checkout session whose metadata carries `crowe_email` and
  `plan_id`, which is what the control plane's webhook
  (`api.crowelogic.com/api/billing/webhook`, `_provision_from_checkout`)
  reads to stamp `crowe_tier` on that Keycloak user when payment lands.
- Stripe returns the buyer to `crowelm.com/welcome`, which the edge turns into
  `/oauth2/sign_out` then `/oauth2/start` back to the shell with `?upgraded=1`,
  so the new session carries the new tier. `/pricing` (a cancelled checkout)
  lands in the shell with the card open.

**The edge is fail-soft on its first apply.** An empty groups header passes
the 402 gate, and `allowed_roles = ["crowelm-app"]` still decides who can sign
in at all. Both are deliberate: the `crowelm-app` Keycloak client was created
after the realm-wide claim-mapper audit, so until one real sign-in shows a
tier at `/app/whoami`, a strict gate could lock a paying member out of what
they pay for. When it does show: switch `@unpaid_model` to the strict matcher
commented beside it in the Caddyfile, drop `allowed_roles` from
`oauth2-proxy.cfg`, re-apply, and the door is the plan. If it does not show,
the fix is additive and on the Keycloak side:
`python3 ~/Projects/crowe-logic-foundry/onboarding/onboard.py fix-mapper`
(or add the "crowe tier" protocol mapper to the `crowelm-app` client by hand).

What a free account can do on the web is therefore: sign in, see the shell,
read its own sessions, and upgrade. It cannot spend model budget.

## What is not covered here

The Caddyfile that serves `/app`, decorates `/app/gw/v1` and `/app/owui/api`
with credentials, and guards the whole thing, lives on the VM and is being
brought under version control on the `feat/one-identity-edge` branch of
`crowelm-platform`. Two of the changes in this branch depend on lines in that
file: the named-agents catalog needs `/app/owui/api/models` exposed, and the
identity change replaces basic auth with Crowe ID. Until those are applied the
web build behaves exactly as before on both counts.
