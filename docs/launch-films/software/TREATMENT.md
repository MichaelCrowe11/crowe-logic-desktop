## Dramatic question

A progress summary is wrong. Can you hand off the repair and still explain exactly what was changed, what was refused, what was tested and what remains uncertain?

The entire film stays inside one original example project, **Queue Notes**, a tiny task-summary utility. An archived task lowers its completion percentage and an empty list returns an invalid percentage. The problem is deliberately planted for teaching and identified as such. It is not a customer incident and not a defect in the Crowe Logic app. The audience understands the expected result without needing the app's private source.

This is a story about decisions, not a list of controls. Opening question: why is a finished list only half complete? Middle: a plausible shortcut is rejected because it changes the wrong meaning. Turn: an actual test challenges the repair. Ending: the next person can inspect the change and its evidence without replaying an entire conversation.

## Chapter treatments

### S1. One wrong number

Start on the sample's two rows: one done, one archived. Pair them with a real invocation of the intentionally buggy summary showing 50 percent, then the written requirement that archived rows are outside the active list. The problem is small enough to reason about. Establish the expected 100 percent as the sample's specification, not a response supplied by an assistant. Introduce the actual installed product and a dedicated example project, not the desktop's home directory. Keep the fictional/example label visible when it matters.

### S2. Ask for a plan

Stay on one task thread. The instruction is to investigate without changing files. Record the actual read sequence, then the actual plan. The editor is not entitled to fourteen tool calls, a particular model sentence or a specific latency from the old film. Make the unchanged project a separate evidence item, not an inference from a polished answer. One question anchors the act: which calculation should change, and which behavior should stay the same?

### S3. Read the contract

Use the sample's plain requirements and six tests to teach the difference between an observation and an assumption. Include an empty list and an all-archived list; they give the film a second problem rather than repeating the first. Compare the denominator to the meaning of active work. If a shell request is refused at the selected read-only tier, retain its actual explanation; if no call is attempted, do not call the verbal refusal a hostile-tool enforcement test.

### S4. Choose the change

The critical decision is not "trust the computer." It is whether the proposed patch follows this contract. Reject a genuine overbroad or wrong proposal if one occurs. If the first patch is correct, use a separately requested, clearly operator-authored demonstration change to `handoff-draft.txt`, then deny that proposal; do not script a fake agent mistake. No silent reset and no blended take suggesting a rejection that never occurred. Approve only a narrow reviewed change. Show the actual saved diff, keeping the pending card and applied result distinct. Authorize any test additions separately. No shell execution is necessary to demonstrate a file proposal.

### S5. Make it answer a test

The operator deliberately permits execution and runs the sample's existing acceptance command. A real failure remains in the story until fixed and tested again, within a bounded take budget. A first-pass success is not less interesting; show why the tests cover the contract. Do not inherit the Harness's 85-test claim. Treat the verifier's own status and engine disclosure literally. If it reports skipped or inconclusive, the narrator says what was checked and leaves that distinction intact. The sample output and command evidence, not a green badge alone, close this act.

### S6. Invite a critical reader

The second reader gets the requirements, final diff and real tests. Ask for a concrete counterexample, not applause. Only a roster already accepted as customer-safe is eligible. A same-engine separate pass is never called independent. The reviewer may find a gap or correctly find none; either can serve the story if grounded. There is no quota of invented criticism. When a gap is found, the operator chooses whether to repair or record a limitation. Workers do not need execution rights for this act.

### S7. Leave a usable handoff

Create a concise handoff file in the sample project through the product's real approval path: original defect, actual change, exact command, result and open questions. Reopen the same synthetic profile after an orderly app quit. Verify which files and conversation content return; do not promise every live tool card is reconstructed. Compare persisted files, not staged screenshots. Keep "saved work" separate from automatic backup, cloud synchronization or full-machine recovery. An optional browser research chapter is omitted: a local sample is sufficient, and no browser capability was qualified in this pass.

### S8. A deliberate next step

Return to the exact initial task rows and resulting summary, now backed by the requirements and tests. The answer to the opening question is the visible chain of decisions. Identify the qualified edition and exact supported platform only after release acceptance. Use one verified entry address in voice, end card and metadata. This is a licensed-app CTA, never an invitation to read proprietary product source. The final product claim is a placeholder until the installed artifact and public route agree.

## Capture-bound prompt cards

These are operator requests for a future authorized session, not expected assistant text.

- Plan: "In this original Queue Notes example, archived tasks lower the completion percentage and an empty list produces an invalid percentage. Read REQUIREMENTS.md and the source, then propose an investigation. Do not change files or run commands."
- Read: "Compare summary.cjs with the requirements and six existing tests. Identify the smallest behavioral mismatch. Do not edit files or run commands."
- Edit: "Propose the smallest repair that satisfies the documented active-task and empty-list behavior. Preserve inputs and the function interface. Show changes for review; do not run commands."
- Optional rejection demonstration: "Propose adding the sentence 'Example only; not a deployment receipt.' to a new handoff-draft.txt. Wait for my review." Deny it once if needed; verify no file was created. It must be narrated as an operator-requested demonstration, not an assistant error.
- Execute: "Run only node --test summary.test.cjs in this example project. Report the actual result, including any failures. Do not install anything or contact external services."
- Review: "Read the requirements, actual diff and tests. Find a concrete remaining counterexample if one exists. Do not change files or run commands. Say what you could and could not verify."
- Handoff: "Propose a short HANDOFF.txt with the defect, changes, exact executed test command and observed result, and any unresolved limits. Do not claim deployment or independent review."

The requests do not grant this document session permission to call a model. Future capture must use genuine product responses, never injected fixtures portrayed as autonomous work.
